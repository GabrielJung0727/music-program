# 인수인계

2026-11-16 저녁 기준, 같은 날 밤 두 번째 PC 에서 0 ~ 3장을 고쳐 적었다. 다른 PC 에서 이어서 하기 위한 문서다.

함께 읽을 것: [`DESIGN.md`](DESIGN.md)(디자인 규칙), [`README.md`](README.md)(실행 방법), [`../docs/07-백엔드-점검.md`](../docs/07-백엔드-점검.md)(Core 점검 결과).

## 0. 맨 먼저 할 일

`fix/core-hardening` 은 `development` 에 합쳐졌다(PR #5 · #6). `development` 를 받는다.

```powershell
git fetch origin
git checkout development
git pull
$env:DOTNET_ROLL_FORWARD = "Major"   # .NET 8 런타임이 없는 PC 라면. .NET 10 위에서 돈다
```

2026-11-16 밤, 두 번째 PC 에서 처음 돌렸다. **293개 모두 통과**했다(새로 쓴 `HardeningTests` 41개 포함).
4장은 이제 참고용이다. 같은 날 2 · 3단계(실제 Core 로 확인)도 했다. 결과는 3장의 체크 표시와 3.1 "새로 찾은 것".

로컬에서 띄우기: `.claude/launch.json` 에 `mono-core`(Core, `-p:RollForward=Major`), `mono-web`(기존 화면 5273),
`mono-redesign-real-core`(새 화면 5373 → 실제 Core)가 있다. 출력 워커는 셸 없이도 붙일 수 있다:
`src/Mono.Output/bin/Debug/net8.0/Mono.Output.exe --host=127.0.0.1 --room=<방 id>` (방 id 는 `GET /api/rooms`).

## 2. 작업 순서

1. **테스트.** 0장. 통과할 때까지 고친다. **건너뛸 수 없는 0단계다.** 이게 끝나기 전에는 5번 이후의 코드를 쓰지 않는다.
   테스트 안 된 수정 20여 건 위에 구조 변경을 얹으면, 깨졌을 때 어느 쪽 탓인지 가를 수 없다.
2. **고친 Core 를 띄워 기존 화면으로 확인.** `dotnet run --project src/Mono.Control`. 3장의 "Core 변경" 목록.
   기존 화면(`src/Mono.Web`)이 그대로 돌아가야 한다. 여기서 문제가 나오면 화면이 아니라 Core 수정의 문제다.
3. **새 화면을 실제 Core 에 붙여 확인.** 3장의 "새 화면" 목록.
   ```powershell
   dotnet run --project src/Mono.Core
   cd redesign; npm install
   $env:CORE = "http://127.0.0.1:7702"; npm run dev     # http://127.0.0.1:5373
   ```
4. **Core 변경을 먼저 합친다.** 화면 이식과 별개로 릴리스할 수 있다. 보안 수정이라 기다릴 이유가 없다.

   1 ~ 4 는 2026-11-16 에 끝났다. 2 · 3 에서 못 본 것(TIDAL, 큰 라이브러리, 다른 PC 출력, 모션, `Mono.Control` 셸)은 3장에 빈칸으로 남겼다.
5. **남은 Core 과제 중 답이 필요 없는 것.** 8장의 "답 없이 할 수 있는 것" 네 가지. 3.1 의 2 · 3 도 여기서 정하면 좋다.
6. **화면 이식.** 6장.
7. **출시를 막는 것 풀기.** 9장.
8. **릴리스.** 7장.

8장의 질문 넷에 대한 답은 아무 때나 받아 두면 된다. 답이 걸린 작업은 그 뒤에 시작한다.

## 3. 확인 목록

### Core 변경 (기존 화면으로)

2026-11-16 밤에 두 번째 PC 에서 본 결과. 라이브러리는 무음 FLAC 6곡(24/96 커버 있음 3곡, 16/44.1 커버 없음 3곡)이었다.
Core 쪽은 WebSocket 으로 명령을 직접 보내는 스크립트와 기존 화면으로 봤다.

- [x] 화면이 뜨고 사이드의 연결 표시가 정상이다. REST 는 낯선 `Host` · 외부 `Origin` 이면 403, 로컬은 200.
- [x] 재생, 일시정지, 탐색, 다음 곡(자동으로 넘어감), 대기열 순서 바꾸기.
- [x] 라운지 열기와 닫기. 다른 연결로 손님 입장.
- [x] 손님이 나간 뒤 다시 들어올 수 있다. 호스트가 방을 닫은 뒤 손님이 "나가기"를 눌러도 오류가 뜨지 않는다.
- [x] DSP 끄기가 실제로 꺼진다. 출력 워커를 붙인 방에서 `bitPerfect` 가 켜면 false, 끄면 true 로 돌아왔다.
- [ ] TIDAL 로그인. 계정이 없어 못 봤다.
- [x] 없는 경로를 스캔하면 폴더가 생기지 않고 곡 수도 그대로다. (폴더 선택은 셸이 필요해서 `scan_library` 로 봤다.)
- [ ] 큰 라이브러리에서 Core 가 전보다 빨리 뜬다. 라이브러리가 작아 못 쟀다.
- [x] 대기열 마지막 곡에서 자동 재생 후보가 뜨고, 곡이 끝나면 후보가 이어서 재생된다.

- [x] 외부 `Origin` 의 WebSocket 은 403. `Origin` 이 없거나 루프백이면 101, `Origin: null` 은 403.

### 3.1 새로 찾은 것 (2026-11-16 밤)

1. **다시 붙은 화면이 방에서 빠진 채 멈춰 있었다. 고쳤다.** Core 는 끊긴 연결을 먼저 알아채면 그 사람을 방에서 뺀다.
   peer id 는 비밀값으로 되찾지만 멤버 자리는 되찾지 않는다. 그런데 두 화면 모두 다시 붙은 뒤 방에 다시 들어가지 않아서,
   방 상태를 받지 못한 채 멈춘 화면이 남았다. 화면의 소켓을 닫아 재현했다(닫은 뒤 그 peer 가 멤버 목록에서 사라짐).
   `MonoProvider.tsx`(양쪽 같은 파일)가 다시 붙으면 있던 방에 `join_room` 을 보낸다. 초대 전용 방이면 들어갈 때 쓴 코드를 같이 낸다.
   방이 그 사이 사라졌으면(Core 재시작 등) 조용히 비우고, 다음에 곡을 틀 때 새 솔로 방을 만든다. 두 경우 모두 브라우저에서 확인했다.
   **남은 것(Core):** 손님이 있는 방에서 호스트의 연결이 먼저 끊긴 것으로 처리되면 호스트가 손님에게 넘어간다(`RoomManager.Leave`).
   다시 들어와도 청취자다. 호스트 PC 의 화면은 루프백이라 드물지만, 원격 Control 이 호스트일 때는 일어날 수 있다.
2. **대기열이 끝난 뒤 "이어서 재생"이 아무 일도 하지 않는다.** 마지막 곡이 끝나 멈춘 상태에서 앨범 화면의 "이어서 재생"이나 플레이어 바의 재생을 누르면,
   Core 의 `play` 가 끝 위치에서 다시 시작해 곧바로 끝난다(`RoomManager.Play`). 이번 수정 전부터 그랬다.
   처음부터 다시 틀지, 마지막 곡을 처음부터 틀지 정해야 한다.
3. **새 화면의 "비우기"가 지금 곡까지 지운다.** 버튼은 "다음 N곡" 옆에 있지만 `clear_queue` 는 큐 전체를 비우고 재생을 멈춘다.
   다음 곡만 비우려면 Core 에 그런 명령(또는 플래그)을 더해야 한다. 규약이 바뀌므로 C# 먼저, 그다음 양쪽 `protocol.ts`.
4. **Core 의 영어 오류가 토스트에 그대로 나온다.** 이미 대기열에 있는 곡을 "다음에 재생"하면 `duplicate track in queue` 가 뜬다.
5. **라운지 목록에 방이 하나뿐이면** "가장 많이 모인 방"으로 위에 빠진 뒤, 아래 "열려 있는 방 · 전체"에 "이 조건에 맞는 방이 없습니다"가 뜬다.

## 4. 테스트가 깨질 만한 곳

기존 테스트를 읽어 보고 충돌이 없다고 판단했지만 돌려 보지는 못했다. 깨진다면 아래 중 하나일 가능성이 높다.

| 바꾼 것 | 깨질 수 있는 경우 | 위치 |
| --- | --- | --- |
| 방 id 를 지정한 명령은 멤버만 | 방에 들어가지 않은 peer 로 `commands.Execute(..., RoomId = ...)` 를 부르고 성공을 기대하는 테스트 | `CommandProcessor.NeedRoom`, `RoomManager.IsMember` |
| `leave_room` 을 멤버가 아닌 사람이 보내면 응답이 없다(`default`) | 오류 응답을 기대하는 테스트 | `CommandProcessor` LeaveRoom |
| 솔로 방은 Control 로 주인만 입장 | 솔로 방에 두 번째 Control 이 `Join` 하는 테스트. 출력(`PeerRole.Output`)은 그대로 된다 | `RoomManager.Join` |
| 자동 재생 후보가 없어도 `AutoplayProposedForTrackId` 를 적는다 | 후보가 없을 때 이 값이 null 이길 기대하는 테스트 | `RoomManager.ProposeAutoplayCandidates` |
| `Recommend` 에 카탈로그 전체 수 대신 48 을 넘긴다 | 후보가 49번째 이후에만 있는 경우를 다루는 테스트 | `RoomManager.AutoplayPoolSize` |
| `Scan` 이 없는 폴더를 만들지 않는다 | 폴더가 생기길 기대하는 테스트 | `LibraryScanner.Scan` |
| `EnsureThumbnail` 이 원본 경로를 그대로 돌려준다 | `thumbs` 폴더에 파일이 생기길 기대하는 테스트 | `ArtworkService` |
| `set_dsp` 가 `flag=false` 면 프리셋을 Off 로 | `flag=false` 와 프리셋을 같이 보내고 프리셋이 남길 기대하는 테스트 | `CommandProcessor` SetDsp |
| `Execute` 에 `bool local = true` 인자 추가 | 리플렉션이나 델리게이트로 시그니처를 고정한 곳 | `CommandProcessor.Execute` |
| `MonoMessage` 에 `Secret` 추가 | 필드 수를 세는 테스트 | `MonoMessage.cs` |

새로 쓴 `tests/Mono.Tests/HardeningTests.cs` 가 실패하면, 테스트의 가정이 틀렸을 수도 있다. 특히:
`ChatLinesAreClipped`(채팅이 한 줄로 그대로 들어간다고 가정), `TurningDspOffWithTheFlagClearsThePreset`(솔로 방에서 DSP 가 켜진다고 가정).

## 5. Core 규약에서 알아 둘 것

| 사실 | 화면에서 한 일 |
| --- | --- |
| welcome 이 `secret` 을 준다. 주인이 있는 peer id 는 hello 에 그 값을 돌려줘야 되찾는다 | `controlClient.ts`(양쪽 화면 모두) |
| `list_rooms` 가 `covers` · `nowTitle` · `nowArtist` · `upcoming` 을 싣는다 | 라운지 표지와 "지금 곡" 한 줄. 필드가 없으면(예전 Core) 패턴 표지 |
| `set_dsp` 는 프리셋이 Off(0)면 끈다. 이제 `flag=false` 도 끄기로 받는다 | 끌 때 프리셋 0 을 보낸다. 마지막 프리셋은 `localStorage`(`mono_dsp_preset`) |
| `artUrl` 은 곡에 커버가 없으면 앨범 커버로 물러난다 | 따로 할 일 없음 |
| `/api/wiki/{id}` 는 `extract` · `sourceUrl` 을 보낸다(`summary` 가 아니다) | `rest.ts` 타입, 아티스트 화면 |
| `badge` 는 `24/96000 · Bit-perfect Local` 형식. DR 값이 아니다 | 음질은 `sampleRate` · `bitDepth` 에서 계산 |
| `set_room_flags` 는 호스트만. 자동 재생 플래그는 `smart_autoplay` | 그대로 사용 |
| `set_volume` 은 대상이 없으면 보낸 사람 자신에게 건다 | 출력이 없으면 볼륨을 막아 둠 |
| REST 는 이 PC 에서 온 요청만 받는다(커버 · 상태 확인 · 스트림 프록시 제외) | 따로 할 일 없음 |
| 방을 닫거나 쫓아내도 당사자에게 알림이 가지 않는다 | 화면은 다음 명령이 실패할 때 알아챈다. 고치지 않음 |
| `list_rooms` 는 바뀔 때 밀어 주지 않는다 | 라운지 화면이 8초마다 다시 묻는다 |

원본과 다른 화면 쪽 파일: `lib/rest.ts`(WikiBio 타입), `lib/model.ts`(새 파일), `lib/dsp.ts`(새 파일).
`controlClient.ts` 와 `protocol.ts` 는 `src/Mono.Web` 과 `redesign` 을 똑같이 고쳤다.
`adapters.ts` 와 `data/types.ts` 는 새 화면이 쓰지 않는다. `MonoProvider` 가 가져다 쓰기 때문에 남겨 두었다.

## 8. 정해지지 않은 것

### Core: 남은 과제의 해결안 (`docs/07` 3 · 5장)

제안한 해결안이다. 아직 아무것도 구현하지 않았다.

**답 없이 할 수 있는 것**

1. **곡 id.** id 를 스캔 때마다 파일 이름에서 계산하지 않고, DB 에 한 번 발급해 유지한다.
   - `local_path` 로 기존 행을 찾으면 그 id 를 쓴다.
   - 못 찾으면, 파일이 사라진 행 중 태그(앨범 · 디스크 · 트랙 번호 · 제목 · 길이)가 같은 것의 경로만 갱신한다.
   - 둘 다 아니면 새 id 를 발급한다.
   - 기존 DB 이전은 필요 없다. 살아 있는 곡은 옛 id 를 유지해서 기록 · 플레이리스트 · 커버 캐시가 그대로 맞는다.
   - **규칙:** 태그가 비었거나 맞는 후보가 둘 이상이면 경로를 갱신하지 않고 새 id 를 발급한다. 틀린 행에 붙으면 되돌릴 수 없다.
   - **착수 전에** 라이브러리 사본에서 파일 이름이 겹치는 곡이 몇 건인지 먼저 잰다.
   - 이미 덮어써진 채 쌓인 재생 기록은 되돌릴 수 없다.
2. **7700 · 7701 을 기본 `127.0.0.1` 에만 연다.** "다른 PC 의 출력 허용" 설정을 켜야 LAN 에 열린다.
3. **스트리밍 토큰을 DPAPI(현재 사용자)로 감싼다.** 첫 실행 때 평문 파일을 암호화본으로 바꾼다.
   Core 는 `net8.0`(Windows 전용 타깃이 아님)이라 `System.Security.Cryptography.ProtectedData` 패키지와 `OperatingSystem.IsWindows()` 가드가 필요하다.
   같은 사용자로 도는 악성 프로그램은 막지 못한다. 백업을 다른 PC 에 복원하면 다시 로그인해야 한다.
4. **설치 경로 검증.** 릴리스에 SHA-256 을 올리고 `install.ps1` 이 확인한 뒤에만 실행한다. "인터넷에서 받은 파일" 표시는 해시가 맞을 때만 지운다.
   업데이트 주소를 바꾸는 기능은 개발 빌드에서만 허용한다.

**답을 받은 뒤에 할 것**

5. **GitHub 토큰** (질문 1). 릴리스가 공개면 토큰 코드를 전부 걷어내고 `prefs.ini` 의 값도 지운다.
   비공개면 `gh auth token` 수집을 그만두고, 그 저장소 읽기 전용 토큰만 직접 넣게 한 뒤 DPAPI 로 저장한다.
6. **원격 출력 페어링** (질문 2). 원격 출력 워커는 페어링 토큰을 내야 붙는다(`Mono.Output --host=… --pair=코드`). 출력 id 도 비밀값으로 묶는다.
   여기까지 해도 같은 네트워크의 엿듣기는 못 막는다(키와 토큰이 평문 TCP). 막으려면 7701 에 TLS 를 씌우고 페어링 때 지문을 고정한다.
7. **코드 서명** (질문 4). 후보: CA 의 코드 서명 인증서(키를 하드웨어 토큰이나 클라우드 HSM 에 둬야 함), Azure 서명 서비스(한국에서 가입되는지 확인 필요),

8. **계정** (질문 3). A: 기기 키. Control 이 영구 키를 만들어 보관하고 Core 가 그 키로 사용자를 구분한다. 기록 · 플레이리스트를 사용자별로 나누고,

### 라운지에서 소리가 전달되는 방식

코드에서 읽은 것이다. 실행해 확인하지는 않았다.

- 공개 라운지(OpenLounge)와 HostQueue 방은 Fan-out 이다. 로컬 파일은 Core 가 읽어 방의 모든 출력 워커에 보낸다. 받는 쪽은 그 파일이 없어도 된다(`ListeningRoom.cs`, `FanOutService.cs`).
- 스트리밍 곡은 Fan-out 하지 않고 시각만 맞춘다(`IPlaybackSource.cs`). 다만 방 상태에 실리는 재생 주소는 Core 주인의 계정으로 만든다(`RoomBroadcaster.StateMessage`).
  `/api/stream/tidal/{id}` 는 주인의 토큰으로 TIDAL 스트림을 받아 출력 워커에 넘긴다. 손님마다 자기 계정을 확인하는 코드는 찾지 못했다.
- 정원은 기본 16(화면 연결과 출력 워커를 합쳐 센다), 호스트가 128까지 올릴 수 있다.
- 권리자 허락, TIDAL client id 가 정식 등록 앱인지, Qobuz 의 "앱 토큰" 방식이 승인된 것인지는 확인된 바 없다. **법률 검토가 필요한 항목이다.**
- 화면은 이 기능을 권한다: 첫 실행의 "라운지에서 함께 들을 수 있습니다", 라운지 열기의 "누구나 들어올 수 있습니다".
  실제로 "누구나"는 그 Core 에 연결한 기기뿐이다. 남의 라운지를 찾는 수단은 없다.

### 고지와 표기

- 글꼴 다섯 종은 OFL-1.1, `lucide-react` 는 ISC 다. 상업 배포는 되지만 **앱과 저장소 어디에도 라이선스 고지가 없다.** 저장소 루트에 LICENSE 도 없다.
  설정에 "오픈소스 라이선스" 화면을 두고 글꼴의 저작권 표시와 OFL 전문, ISC 전문을 싣는다.
- `TIDAL` · `Qobuz` · `Discord` 는 글자로만 쓴다(로고 이미지는 없다). 상표 귀속과 제휴가 아니라는 문구가 없다.
- 같은 방의 배지가 호스트에게는 `ON AIR`, 손님에게는 `LIVE` 다. 하나로 맞출지 정한다.

## 10. 손볼 때 지킬 것

- 색 · 글꼴 · 반지름 · 모션은 `DESIGN.md` 와 `src/styles/tokens.css` 에 확정된 값만 쓴다. 새 값이 필요하면 임의로 고르지 말고 정한 뒤 두 곳에 같이 적는다.
- 모션은 다섯 군데뿐이다. 등장 페이드, 호버에서 떠오르거나 커지는 효과, 깜빡이는 램프는 넣지 않는다.
- 앰버는 DSP · SRC 개입에만, 빨강은 On Air 에만 쓴다.
- 화면 문구에 엠대시(—)를 쓰지 않는다. 이모지를 아이콘으로 쓰지 않는다.
- Core 가 보내지 않는 정보를 화면에 지어내지 않는다.
- **모의 Core 는 실제 Core 와 같게 유지한다.** 모의 쪽이 너그러우면 버그가 가려진다. DSP 끄기와 위키 필드가 그렇게 가려져 있었다.
- Core 의 규약을 바꾸면 C# 을 먼저 고치고 `protocol.ts` 를 양쪽 화면에서 같이 고친다.

## 11. 작업한 PC 에만 있는 것

- **캡처.** `redesign/screenshots/` 는 저장소에 없다. 새 화면은 `npm run capture` 로 다시 만든다(모의 Core 와 개발 서버를 먼저 띄운다).
  기존 화면 캡처(`before`)는 스크립트로 만들 수 없다.
- **임시 .NET SDK.** 작업한 PC 의 임시 폴더에만 받아 썼다. 시스템에는 설치하지 않았다.
- **작업 메모.** 대화 기록과 메모는 옮겨지지 않는다. 필요한 것은 이 문서와 `DESIGN.md`, `docs/07` 에 적었다.
- **심의 기록.** 모의 재판의 전문(진술, 반박, 배심원별 표)은 작업한 PC 의 임시 폴더에만 있다. 결론은 9장에 옮겼다.
- **git.** 작업한 PC 에서는 `git.exe` 의 네트워크 연결이 막혀 있어 `fetch` · `push` 가 되지 않았다. 1장의 "원격과 같다"는 마지막으로 받아 둔 정보 기준이다.
