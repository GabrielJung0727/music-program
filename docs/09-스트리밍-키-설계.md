# 스트리밍 파트너 키 설계 (Tidal · Qobuz)

기준일 **2026-11-22** · 대상 버전 0.7.2 이후 · 상태 **결정 반영 · §6 "지금" 단계 구현됨(`feature/partner-keys`) · 파트너 답변 전**

파트너 키를 받았을 때 **어디에 넣고, 누가 볼 수 있고, 새면 어떻게 하는가**를 정한다.
계약을 따내는 일이 아니라, 키가 오는 날 코드와 릴리스 파이프라인이 준비돼 있게 하는 일이다.

---

## 0. 결론

1. **Tidal 은 숨길 비밀이 없다.** PKCE 공개 클라이언트라 Client ID 만 있으면 된다(소스에 이미 있다). 파트너 계약에서 얻을 것은 비밀이 아니라 **프로덕션 Client ID 와 요청 한도**다.
2. **Qobuz 의 App Secret 이 문제다.** 설치 파일은 공개 다운로드라, 안에 넣은 비밀은 누구나 꺼낼 수 있다. "심는다"는 "숨긴다"가 아니다.
   그래서 비밀이 **클라이언트에 있어도 되는지**를 Qobuz 에 먼저 묻고, 그 답이 보관 위치(설치 파일 / 프록시)를 정한다.
3. **지금 계약 없이 할 수 있는 일이 있다.** 키를 읽는 길을 한 곳으로 모으고, 사용자가 키를 직접 넣어야 하는 구조를 없애고, 릴리스 파이프라인에 주입 구멍을 빈 값으로 먼저 뚫어 둔다(§6).

## 1. 지금 코드가 하는 일

> 이 절은 **구현 전**의 코드를 적은 것이다. 무엇이 어떻게 바뀌었는지는 §6 의 표와 §6.1 에 있다.

| 대상 | 현재 | 근거 |
| --- | --- | --- |
| Tidal Client ID | 소스에 상수 `iGGv2a5inmlTZdbY`("QA Client ID"). 환경변수로 덮어쓸 수 있다 | `TidalClient.EmbeddedClientId` |
| Tidal 인증 | OAuth 2.1 **PKCE**, Secret 없이 토큰 교환 · 갱신. Secret 이 env 에 있을 때만 Basic 헤더를 붙인다 | `TidalClient.ExchangeCode` · `PostToken` |
| Qobuz App ID / Secret | 환경변수 `MONO_QOBUZ_APP_ID` · `MONO_QOBUZ_APP_SECRET` 또는 `%LOCALAPPDATA%\Mono\credentials.env`(**평문**). **사용자가 직접 넣는 구조** | `StreamingHub`, `CredentialStore` |
| Qobuz 호출 | `app_secret` 과 `user_auth_token` 을 **URL 쿼리**로 보낸다 | `ExchangeQobuz`, `FetchQobuzFileUrl` |
| 사용자 토큰 보관 | DPAPI(CurrentUser)로 감싼 파일 | `SecretFile` |
| 자식 프로세스 | Control 이 Core **와 Output 모두**에 키 환경변수를 실어 준다 | `ProcessSupervisor.StartSilent` |

두 가지를 바로잡는다.

- **`06-로드맵.md` 는 낡았다**(기준일 2026-09-10). 거기엔 "파트너 키 미발급, 현재 데모 카탈로그"라고 되어 있지만 Tidal 은 이미 실 OAuth·검색·재생 URL 경로를 갖고 있다(테스트도 있다).
  다만 **실제 계정으로 로그인해서 재생하는 것까지 이 문서를 쓰는 동안 확인하지는 못했다.**
- **Qobuz 어댑터는 Qobuz 문서와 대조한 형태가 아니다.** 로그인 주소, `client_id`, `app_secret` 을 쿼리에 싣는 방식은 파트너 문서를 보고 짠 것이 아니라 추정으로 보인다.
  키가 오면 키만 넣는 것이 아니라 **어댑터를 문서 기준으로 다시 쓸 가능성**을 계획에 넣어야 한다.

`CredentialStore.Write` 는 호출하는 곳이 없다. `credentials.env` 는 사용자가 손으로 만드는 파일이고, Mono 는 읽기만 한다.

## 2. 위협 모델

저장소(`GabrielJung0727/music-program`)와 릴리스는 **공개**다.

| 누가 | 할 수 있는 것 | 우리가 막을 수 있나 |
| --- | --- | --- |
| 저장소를 보는 사람 | 소스·git 이력에 있는 값을 읽는다 | **예.** 비밀을 소스와 이력에 한 번도 넣지 않는다 |
| 설치 파일을 받은 사람 | 어셈블리를 열어 상수 · 문자열을 꺼낸다 | **아니오.** 늦출 수만 있다 |
| 같은 PC 의 다른 프로그램 | 환경변수 · `credentials.env` · 프로세스 메모리를 읽는다 | 평문 파일을 없애면 줄일 수 있다 |
| 키를 꺼낸 사람 | 우리 앱인 척 API 를 부른다 → 한도 소진, 계정 정지, **파트너와의 관계 손상** | 폐기 · 교체 절차로 피해 시간을 줄인다 |

**설계의 목표는 "뽑을 수 없게"가 아니라 "저장소에서는 안 새고, 새면 빨리 바꿀 수 있게"다.**
설치 파일 안의 문자열을 XOR · 분할로 가리는 것은 `strings` 로 찾는 사람만 막는다. 하게 되더라도 보안이라 부르지 않는다.

## 3. 원칙

1. **공개 값과 비밀 값을 나눈다.** Tidal Client ID · Redirect 는 공개 값이라 소스에 둔다. Qobuz App Secret 만 비밀이다.
2. **비밀은 소스에 없다.** 릴리스 빌드 때 GitHub Actions 시크릿으로만 들어간다. 이미 서명 인증서(`MONO_SIGN_PFX_BASE64`)가 같은 방식이다.
3. **키는 Core 프로세스만 가진다.** Output · Control · Setup 에는 실어 주지 않는다.
4. **사용자는 키를 만지지 않는다.** 환경변수 · `credentials.env` 는 개발자·고급 사용자용 덮어쓰기로만 남기고, 화면에는 어느 키를 쓰는지만 보여 준다.
5. **키가 없어도 앱은 멀쩡하다.** 로컬 빌드, 포크, 키 폐기 직후 모두 데모 또는 "이 서비스는 지금 쓸 수 없음"으로 정상 동작한다.
6. **교체할 수 있다.** 설치 파일에 박은 키는 자동 업데이트로만 바뀐다(§5).

## 4. 구성

### 4.1 한 곳으로 모으기 — `PartnerKeys`

지금은 `Env("MONO_…")` 가 `TidalClient` 와 `StreamingHub` 곳곳에 흩어져 있다. Core 안에 하나를 둔다.

```
PartnerKeys.Tidal.ClientId            // 공개 값
PartnerKeys.Qobuz.AppId
PartnerKeys.Qobuz.AppSecret           // null 일 수 있다
PartnerKeys.Source(provider)          // Override | Build | None
```

해석 순서: **덮어쓰기**(환경변수 · `credentials.env`) → **빌드에 주입된 값** → **없음**.
`HasLiveCredentials`, 화면의 "내장 키 / 사용자 키 / 데모" 표시, 로그가 전부 이 한 곳을 본다.

### 4.2 빌드 주입

```
GitHub 시크릿 ──▶ release.yml env ──▶ publish.ps1 ──▶ -p:QobuzAppSecret=… ──▶ obj/PartnerKeys.g.cs (git 무시) ──▶ Mono.Core.dll
```

- 시크릿이 비어 있으면 빈 값이 들어가고 `Source = None` 이다. 로컬 빌드와 포크가 이 경우다.
- 생성 파일은 `obj/` 에만 둔다. 커밋할 수 없는 위치다.
- GitHub Actions 는 시크릿을 로그에서 가려 준다. `publish.ps1` 이 값을 `Write-Host` 하지 않게 한다.
- **공개 저장소라 포크한 PR 의 워크플로에는 시크릿이 전달되지 않는다.** 의도한 동작이다.

### 4.3 비밀이 서버에만 있어야 한다면 — 프록시 (조건부)

Qobuz 가 "Secret 은 서버에서만"이라고 하면 설치 파일에 넣을 수 없다. 그때만 얇은 프록시를 둔다.

- 대신 해 주는 일은 **코드 교환과 요청 서명**뿐이다. 사용자 토큰을 프록시가 저장하지 않는다. 가능하면 서명 대상에 토큰이 들어가지 않게 한다(파트너 문서가 정한다).
- 호스팅: 이미 `tools/mono-qa` 가 Vercel 을 쓰고 있다. 무료 한도 안에서 시작할 수 있다.
- 대가: **서버가 없다는 지금의 성질이 깨진다.** 프록시가 죽으면 Qobuz 가 멈추고, 남용 방지(설치별 한도)와 운영이 새로 생긴다.
- 얻는 것: 키 교체가 앱 업데이트 없이 즉시 된다.

기본안은 **클라이언트 보관**이다. 프록시는 파트너가 요구할 때만 쓴다.

## 5. 새면 어떻게 하나

1. 파트너에 폐기와 재발급을 요청한다.
2. GitHub 시크릿을 새 값으로 바꾼다.
3. 패치 릴리스를 낸다. 설치된 앱은 업데이트로 받는다(0.7.2 가 나간 경로와 같다).
4. 그동안 앱이 해당 서비스에서 401/403 을 받으면 "업데이트가 필요합니다"를 보여 준다. 크래시나 빈 화면이 아니어야 한다.

프록시라면 2~3 이 서버 값 교체 한 번으로 끝난다.
**한계:** 업데이트를 안 한 사용자는 그 사이 해당 서비스를 쓸 수 없다. 데모로 떨어지지 않고 안내만 보여야 한다.

| # | 일 | 상태 · 근거 |
| --- | --- | --- |
| 1 | `PartnerKeys` 로 키 읽기를 한 곳에 모으고, 화면에 키 출처를 표시한다 | ✅ `Mono.Core/PartnerKeys.cs`. 어댑터는 환경변수를 직접 읽지 않는다. 설정 › 스트리밍 계정에 "시험용 기본 키 / 내장 키 / 사용자 지정 키"가 나온다. 값은 화면으로 나가지 않는다(테스트로 고정) |

| 3 | 키가 없는 빌드에서 **사용자에게 앱 토큰을 요구하는 길을 없앤다** — "준비 중" | ✅ 탐색 · 첫 실행 · 설정 · 로그인 창 4곳. **Core 도 거절한다**(`link_streaming`), 연결 끊기는 계속 된다. 개발자는 `MONO_QOBUZ_DEMO=1` 로 시험용 곡을 쓸 수 있다 |
| 4 | `release.yml` → `publish.ps1` → 생성 파일 주입 경로를 **빈 값으로 먼저 개통**하고, 빈 값 · 채운 값 두 경우를 확인한다 | ✅ 아래 §6.1. 가짜 값으로 두 경우와 잘못된 문자 입력을 직접 빌드해 확인했다 |
| 5 | 로그에 키 · 토큰이 안 남는지 확인한다 | ✅ 지금 로그에 찍히는 곳은 찾지 못했다. 그래도 `LogRedact` 를 `AppLog` 와 `TidalClient.LastError` 에 걸어 두었다 |

#### 6.1 빌드 주입을 확인한 결과

가짜 값(`FAKE_…`)으로 `dotnet build` 를 세 번 돌렸다.

| 경우 | 결과 |
| --- | --- |
| 값 있음 | 생성된 `obj/…/PartnerKeys.g.cs` 에 값이 들어갔다. **`Mono.Core.dll` 안에서 UTF-16 문자열로 그대로 보인다** — §2 에서 말한 "설치 파일에서 꺼낼 수 있다"를 확인한 것이다 |
| 허용되지 않는 문자(`"` `;` 등) | 빌드가 실패한다. 오류 메시지에 값은 없다 |
| 다시 값 없음 | 생성 파일이 빈 값으로 바뀌고, dll 에서 값이 사라진다 |

빌드 주입용 이름은 `MONO_BUILD_*` 이고 런타임 덮어쓰기용 `MONO_*` 와 다르다. 개발자의 개인 키가 실수로 빌드에 구워지지 않게 하려는 것이다.

#### 6.2 키를 받으면 하는 일

1. GitHub 시크릿에 넣는다. 값은 화면에 남지 않게 프롬프트로 입력한다.
   ```powershell
   gh secret set MONO_BUILD_QOBUZ_APP_ID
   gh secret set MONO_BUILD_QOBUZ_APP_SECRET
   gh secret set MONO_BUILD_TIDAL_CLIENT_ID     # 프로덕션 Client ID 를 받았을 때만
   ```
2. 태그를 푸시하면 `release` 워크플로의 패키징 단계에만 들어간다. "빌드 · 테스트" 단계에는 일부러 넣지 않았다 — 테스트는 언제나 키 없는 빌드로 돈다.
3. `publish.ps1` 이 어떤 키가 들어갔는지 **있음 / 없음**만 로그에 찍는다.
4. 그다음이 §6 "키를 받은 뒤"의 7번(Qobuz 어댑터를 문서 기준으로 다시 쓰기)이다. 키만 넣어서는 Qobuz 가 완성되지 않는다.

## 7. 파트너에게 물을 것

**Tidal**
- 프로덕션 Client ID 발급. 지금 쓰는 값은 QA 용이다.
- 요청 한도(429)가 **앱 단위인가 사용자 단위인가**, 상향이 가능한가. 지금 곡 가져오기가 한도에 걸리는 문제와 직결된다.
- 루프백 Redirect(`http://127.0.0.1:7702/oauth/callback`) 허용.
- 재생 스코프와 제공 음질, 표기 · 상표 요건.

**Qobuz**
- 인증 흐름과 공식 문서.
- **App Secret 을 데스크톱 클라이언트에 둬도 되는가.** 이 답이 §4.3 을 정한다.
- 요청 한도, 스트림 URL 사용 조건(캐시 · 저장 금지 등).
- 폐기 · 재발급 절차와 연락 창구.

**공통**
- Mono 의 라이선스 모델: 스트리밍은 **각자 구독으로 각자 재생하고 시간만 맞춘다(Clock-sync). 스트림 오디오를 다른 사람에게 전달하지 않는다.** 팬아웃은 로컬 파일만. 이 점을 먼저 설명한다.

## 8. 결정 (2026-11-22)

1. **보관 위치: 클라이언트 보관.** 프록시는 파트너가 요구할 때만(§4.3). Qobuz 의 답에 따라 다시 연다.
2. **Release 빌드에서도 사용자 덮어쓰기를 허용한다.** 환경변수 · `credentials.env` 로 자기 키를 쓸 수 있다. 대신 설정 화면이 어느 키를 쓰는지 보여 준다. 덮어쓴 App ID 에는 우리 빌드의 Secret 을 붙이지 않는다(테스트로 고정).
3. **키 없는 빌드의 Qobuz 는 "준비 중"으로 보여 준다.** 숨기지 않는다. 연결 버튼은 꺼지고 토큰을 묻지 않는다.

## 9. 아직 열려 있는 것

- 위 구현은 **파트너 답변 없이 할 수 있는 부분까지**다. Qobuz 어댑터가 파트너 문서와 맞는지, Secret 을 URL 쿼리로 보내는 것이 허용되는지는 문서를 받아야 안다(§6 7번).
- Tidal 의 실제 계정 로그인 → 재생은 이 작업에서 확인하지 않았다.
- `06-로드맵.md` 의 "현재 데모 카탈로그"는 Tidal 에 대해 낡았다. 이 문서의 §1 이 현재 코드 기준이다.
