# 백엔드 점검

2026-11-16. 대상은 `src/Mono.Core`, `Mono.Output`, `Mono.Protocol`, `Mono.Shared`, `Mono.Control`, `Mono.Setup`, 릴리스 스크립트.
새 Control UI(`redesign/`)를 얹기 전에, 문제가 될 만한 것과 보안 위험을 찾아 고칠 수 있는 것부터 고쳤다.

**검증 수준.** 고친 코드는 .NET 10 SDK 로 빌드했다(경고 0, 오류 0). 테스트는 돌리지 못했다 —
작업한 PC 의 Windows 애플리케이션 제어 정책이 새로 빌드한 테스트 DLL 로딩을 막는다.
`tests/Mono.Tests/HardeningTests.cs` 를 새로 썼지만 컴파일까지만 확인했다. **합치기 전에 `dotnet test Mono.slnx` 를 반드시 돌린다.**

아래에서 "확인함"은 해당 코드를 직접 읽고 확인했다는 뜻이고, "분석"은 코드 분석에서 나왔지만 따로 재확인하지 않았다는 뜻이다.
실행해서 재현한 것은 없다.

## 1. 전제: Core 에는 로그인이 없다

Core 는 "이 PC 에서 온 연결은 주인, 페어링 코드를 받은 원격 연결은 손님"이라는 가정으로 움직인다.
그런데 그 가정을 지키는 확인이 여러 군데 빠져 있었다. 가장 큰 세 가지:

1. **아무 웹 페이지나 Core 에 명령을 낼 수 있었다.** 브라우저로 방문한 페이지가 `ws://127.0.0.1:7702/ws/control` 을 열면
   루프백 연결로 취급되어 페어링 없이 모든 명령이 통했다(WebSocket 에는 CORS 가 적용되지 않는다).
   그 페이지는 폴더 스캔, 스트리밍 계정 해제·교체, 원격 접속 코드 발급까지 할 수 있었다.
2. **peer id 를 적어 보내면 그 사람이 됐다.** 방의 권한(호스트·DJ)은 전부 peer id 비교인데, id 는 접속하는 쪽이 고르고
   호스트의 id 는 스냅샷으로 방의 모두에게 보인다. hello 에 호스트의 id 를 적으면 방을 넘겨받았다.
3. **방 id 만 알면 그 방에 명령을 낼 수 있었다.** 멤버인지 확인하지 않아서, 초대 전용 방에 초대 없이 채팅을 쓰거나
   쫓겨난 사람이 그대로 돌아올 수 있었다.

### 동작이 달라지는 점

- **이름(도메인)으로 Core 에 접속하던 환경**은 `Mono:AllowedHosts` 에 그 이름을 적어야 한다.
- **다른 기기의 브라우저에서 REST 를 직접 부르던 스크립트**가 있다면 막힌다.
- **peer id 를 직접 정해 다시 붙던 클라이언트**는 비밀값 없이는 새 id 를 받는다. `Mono.Cli` 는 처음 붙을 때 고른 id 를 그대로 쓴다.
- **방에 들어가지 않고 방 id 로 명령을 보내던 사용법**(CLI 에서 `spectate` 를 입장 대신 쓰는 경우 등)은 먼저 `join_room` 을 해야 한다.
- **페어링으로 붙은 원격 Control** 은 스캔·백업·스트리밍 연결·페어링 코드 발급을 할 수 없다.
- `?w=` 로 커버를 요청해도 원본이 온다. `data/art/thumbs` 폴더의 기존 사본은 지워도 된다.

## 3. 남은 문제 — 결정이 필요한 것

고치려면 구조나 사용 방식을 바꿔야 해서 손대지 않았다.

### 3.1 계정과 신원

- **계정 체계가 없다.** 사람을 구분하는 것은 표시 이름과 peer id 뿐이다. 이번에 넣은 비밀값은 "같은 연결의 주인"만 증명한다.
  재생 기록(`history`)·플레이리스트·아카이브는 peer id 기준이거나 전역이라, 같은 Core 를 쓰는 사람끼리 서로의 것을 볼 수 있다. (분석)
- **쫓아낸 사람은 새 id 로 다시 들어온다.** 차단이 peer id 기준이다. (분석)
- 라운지를 인터넷으로 열 계획이라면 계정(또는 최소한 기기 단위의 영구 키)과, 주인/손님 권한을 나누는 모델이 먼저 필요하다.
  지금 구조는 "같은 집, 아는 사람" 전제다.

### 3.2 MATP 7701 과 TCP 7700

- **두 포트가 모든 인터페이스(`0.0.0.0`)에 고정으로 열린다.** 설정 키가 없다. (확인함: `CoreHostedService.cs` `TcpListener(IPAddress.Any, port)`)
- **7701 에는 인증이 전혀 없다.** LAN 의 누구든 출력 워커인 척 붙어, 다른 출력의 id 를 가로채고 방의 스냅샷(초대 코드·채팅·로컬 파일 경로)과
  오디오 복호 키를 받을 수 있다. 키는 평문 TCP 로 간다. (분석)
- 다른 PC 의 출력 워커를 쓰는 사용자가 있어서 기본값을 루프백으로 바꾸면 그 구성이 깨진다. 그래서 건드리지 않았다.
  권하는 방향: 기본을 루프백으로, LAN 은 설정으로 켜게 하고, 출력 워커도 페어링 토큰을 내게 한다.
- zone 명령(`zone_remove_member` 등)은 이제 루프백만 낼 수 있지만, 루프백 안에서는 여전히 남의 출력을 옮길 수 있다. (분석)

### 3.3 비밀 정보

- **스트리밍 토큰이 평문이다.** `streaming.json` 에 access·refresh 토큰이 그대로 있다. (확인함)
  DPAPI(`ProtectedData`, CurrentUser)로 감싸는 것을 권한다. 같은 사용자로 도는 악성 프로그램은 막지 못하지만 파일이 유출되거나 백업·동기화에 섞여 나가는 경우는 막는다.
- **GitHub 토큰을 가져와 평문으로 저장한다.** `gh auth token` 의 결과를 `prefs.ini` 에 적는다(업데이트 확인용). (확인함: `AppUpdater.cs`, `WizardForm.cs`)
  저장소가 공개라면 필요 없고, 비공개라면 릴리스만 읽는 전용 토큰으로 바꾸는 편이 낫다. `gh` 토큰은 권한 범위가 넓다.
- Qobuz 는 앱 비밀값과 사용자 토큰을 URL 쿼리에 실어 보낸다. (분석)
- `/api/stream/tidal/{id}` 는 인증 없이 주인의 토큰으로 스트림을 대신 받아 준다. 원격 출력 워커가 쓰는 길이라 열어 두었다. (확인함)

### 3.4 릴리스와 업데이트

- **CI 빌드는 서명되지 않는다**(`-NoSign`). 설치 스크립트와 Setup 은 "인터넷에서 받은 파일" 표시(Zone.Identifier)를 스스로 지운다. (확인함)
  SmartScreen 경고를 피하려는 것이지만, 사용자가 서명 없는 실행 파일을 경고 없이 돌리게 된다. 코드 서명 인증서가 근본 해결이다.
- `MONO_UPDATE_FEED` 환경 변수나 `prefs.ini` 의 `update_feed` 로 업데이트 주소를 아무 곳으로나 바꿀 수 있다. (분석)
- Setup 이 `gh` 를 경로 없이 실행한다. Setup 을 내려받은 폴더에 `gh.exe` 가 놓여 있으면 그게 실행될 수 있다. (분석)

## 5. 업그레이드

- **.NET 8 → .NET 10.** 모든 프로젝트가 `net8.0` 이다. .NET 8 의 지원은 2026-11-10 에 끝났다. 자체 포함(self-contained) 배포라
  보안 패치는 새 런타임으로 다시 빌드해야 들어오는데, 8 에는 더 나오지 않는다. CI 는 이미 10 SDK 를 깔고 있다.
  `TargetFramework` 와 `Microsoft.Data.Sqlite`(8.0.11)를 함께 올리고 테스트를 돌리면 된다. 이번에는 올리지 않았다 — 테스트를 못 돌리는 상태에서 런타임을 바꿀 수 없었다.
- **`global.json` 이 없다.** `.slnx` 는 SDK 9.0.200 이상이 필요한데 고정돼 있지 않다.
- **테스트가 릴리스 때만 돈다.** `release.yml` 에만 있다. PR 마다 `dotnet build` · `dotnet test` · `npm run typecheck` 를 돌리는 워크플로를 권한다.
- 패키지: TagLibSharp 2.3.0, NAudio 2.2.1, WebView2 1.0.2903.40, Velopack 1.2.0(세 자리 버전만 받아서 `publish.ps1` 에 변환 표가 있다), DiscordRichPresence 1.3.0.28. 새 버전이 있는지는 확인하지 않았다.
- 테스트가 없는 영역: 연결·인증(이번에 일부 추가), MATP 프레임, 출력 워커의 수신 루프, 동시성, DSP.

## 6. 새 화면이 백엔드에 바라는 것

이번에 넣은 것: 목록의 커버·지금 곡, 앨범 커버로 물러나는 `artUrl`, `flag` 를 보는 `set_dsp`.

아직 없는 것:

- **`list_rooms` 가 바뀔 때 밀어 주지 않는다.** 화면이 8초마다 다시 묻는다.
- **방에서 내보내진 사람에게 알림이 없다.** 화면은 다음 명령이 실패해야 알아챈다.
- **스캔 진행률이 없다.** 설정 화면은 "스캔 중…"만 보여 줄 수 있다.
- **카탈로그를 나눠 받을 수 없다.** 큰 라이브러리에서는 첫 화면이 카탈로그 전체를 기다린다.
- **새로 고침하면 다른 사람이 된다.** 웹 클라이언트는 peer id 를 메모리에만 들고 있어서, 창을 새로 고치면 새 id 를 받고 열어 둔 라운지의 호스트 자리를 잃는다. id 와 비밀값을 세션에 남기고 Core 가 짧은 유예 시간을 두면 해결된다.
