# Mono 아키텍처 — 3단 분산 오디오 시스템

Roon과 같이 기능을 단일 프로세스에 묶지 않는다. **Core / Control / Output** 세 모듈은 같은 기기에서 돌 수도 있고, 네트워크로 분리될 수도 있다.

```
┌──────────────────┐    명령·메타·룸 상태     ┌──────────────────┐
│   Mono Control   │ ◄──────────────────────► │                  │
│   (UI 전용)       │       :7700 / :7702      │    Mono Core     │
└──────────────────┘                          │   (서버/두뇌)     │
                                               │  라이브러리       │
┌──────────────────┐    MATP 오디오+클럭      │  DSP · 큐 · 룸    │
│   Mono Output    │ ◄──────────────────────► │  마스터 클럭      │
│  (DAC 엔드포인트) │         :7701            └──────────────────┘
└──────────────────┘
```

## 1. 3단 역할

### Mono Core (서버/두뇌)

- 음원 카탈로그, 메타데이터 매칭, DSP, 룸/큐 상태, **기기 간 동기화 마스터 클럭**.
- 무거운 연산(업샘플, 컨볼루션, 대량 쿼리)은 여기만 수행한다.
- Windows / macOS / Linux 백그라운드 서비스로 구동한다.

### Mono Control (클라이언트/UI)

- Core에 붙어 명령과 시각화만 담당한다.
- **오디오 콜백을 돌리지 않는다.** 폰으로 룸을 조작하고 소리는 별도 DAC Output에서 난다.
- 현재 두 종류: Core가 서빙하는 웹 UI(`wwwroot`, SignalR), 같은 프로토콜의 CLI(`Mono.Control`).

### Mono Output (오디오 엔드포인트)

- Core로부터 오디오 페이로드를 받아 DAC/드라이버로 출력한다.
- WASAPI **Exclusive**를 먼저 시도하고 실패 시 Shared로 내려간다.
- 클럭 슬레이브: Core가 준 PTS에 맞춰 재생하고, 오프셋·지터·버퍼 깊이를 Core에 되보고한다.

## 2. 기술 스택

| 층 | 선택 | 이유 |
| --- | --- | --- |
| 언어 | C# / .NET 8 | 단일 코드베이스로 Win/macOS/Linux |
| Core 호스트 | ASP.NET Minimal API + BackgroundService | 백그라운드 서비스 + Control UI/API 동시 서빙 |
| 카탈로그 | SQLite (`catalog.db` / `history.db` / `endpoints.db`) | 로컬 우선, 인덱싱된 메타 검색 |
| 전송 | 커스텀 TCP **MATP** + 줄 단위 JSON 컨트롤 프레임 | 바이너리 프레이밍으로 교체하기 쉬운 메시지 계약 |
| 오디오 프레임 | 44바이트 헤더 + AES-GCM 페이로드 | PTS·포맷·epoch·DSD 플래그 |
| Output 렌더러 | NAudio WASAPI (Exclusive→Shared) | 실제 DAC 출력 |
| 태그·커버 | TagLibSharp | FLAC/DSF/MP3 메타 · 내장 아트 |
| 공유 계약 | `Mono.Protocol`, `Mono.Shared` | 세 모듈이 같은 메시지/도메인을 참조 |

상용 UPnP/DLNA에 의존하지 않는다. 오디오 마스터는 항상 Core다.

## 3. MATP — 전송 원칙

1. **컨트롤 플레인**: 룸 참가, 포맷 협상, 볼륨, 클럭 샘플, 큐 포인터, 타임라인.
2. **데이터 플레인**: 타임스탬프가 찍힌 PCM/DSD 청크(`matp_audio`). 소셜 메시지 금지.
3. **클럭**: delay-request/response로 `offset = ((t2-t1)+(t3-t4))/2` 추정 후 지수 평활, 지터는 오프셋 표본의 절대 편차로 추정.
   Output은 `play_at_local = media_origin + (pts − media_time_at_origin) + jitter_buffer − offset`에 출력한다.
4. **적응형 지터 버퍼**: `clamp(5 + rtt/2 + jitter*3, 5, 80)` ms. LAN은 5ms 근처, WAN은 락 유지 우선.
5. **리싱크 epoch**: 시크·트랙 변경·소스 모드 변경 시 `epoch`가 올라가고, Output은 버퍼를 비우고 다시 락한다.
6. **드리프트 보정**: 실제 버퍼 깊이가 목표(지터 버퍼 + DAC 지연)를 넘으면 청크를 흘려보내고,
   크게 이탈하면 한 번에 비운다. 보정 횟수는 Control 측정 UI에 표시된다.

측정 실적(같은 호스트, WASAPI Exclusive): `offset −0.16ms · jitter 0.33ms · rtt 1.96ms · target 6ms`.

## 4. 소셜과 오디오의 격리

- 채팅·핀·관계도 조회는 컨트롤 세션(SignalR/TCP)만 사용한다.
- 팬아웃 송신(`FanOutService`)은 룸별 커서를 두고 재생 헤드보다 **320ms 앞선 구간**을 미리 보낸다.
- 참관(Control-only / 포맷 미지원) 클라이언트는 데이터 플레인에서 제외된다.
- Output은 수신 루프와 렌더 루프를 분리해, 네트워크·JSON 처리 지연이 출력 타이밍에 스며들지 않게 한다.

## 5. 라이선스 재생 모델

- **Clock-sync 모드(스트리밍)**: 각 참가자가 자신의 Tidal/Qobuz/로컬에서 같은 `track_id`를 열고, Core는 타임라인만 방송한다.
  Output은 `local_path`가 있으면 자기 파일을 직접 열어 같은 시각에 재생한다.
- **Fan-out 모드(로컬 라운지)**: Core가 디코드한 청크를 AES-GCM으로 암호화해 Output에 보낸다.
- `PlaybackSourceFactory`는 **소스가 스트리밍이면 룸이 Fan-out이어도 자동으로 Clock-sync로 내린다.**
- 스트리밍 트랙은 해당 계정이 연결돼 있어야 큐에 들어간다(미구독 검증).

## 6. 멀티 디바이스 존 (싱글 플레이)

Zone은 새로운 오디오 경로가 아니라 **Room의 다중 Output 팬아웃을 재사용하는 오케스트레이션 계층**이다.

- **Sync 존**: 존의 멤버 기기를 전부 같은 "개인 방"(`Zone.SyncRoomId`)의 Output으로 묶는다. 한 방이 여러 Output에 동시 방송하는 기존 룸 메커니즘을 그대로 쓰므로 새 동기화 경로가 필요 없다.
- **Independent 존**: 멤버 기기마다 각자의 개인 방(`Zone.IndependentRoomIds[peerId]`)을 배정해, 기기별로 다른 곡을 독립 재생한다.
- 기기를 다른 존/모드로 옮길 때는 `RoomManager.LeaveCurrentRoomAsOutput`으로 소켓 연결은 유지한 채 방 소속만 바꾼다(`EndpointRegistry`의 온라인 상태는 건드리지 않음 — `DetachOutput`과의 핵심 차이).
- 존 자체는 `ZoneRegistry`가 기억하고, 실제 배정 오케스트레이션(방 생성/이동)은 `CommandProcessor.MoveDeviceIntoZone`이 수행한다.

## 7. 솔루션 레이아웃

```
src/
  Mono.Shared      도메인 모델 (트랙·룸·큐·핀·엔드포인트·아카이브)
  Mono.Protocol    MATP 프레임, 메시지 계약, 클럭, LRC 파서
  Mono.Core        카탈로그·룸·타임라인·DSP·팬아웃·서비스 호스트·Control 웹 UI
  Mono.Output      클럭 슬레이브 엔드포인트 + WASAPI 렌더러
  Mono.Control     Core에 붙는 CLI 클라이언트
tests/
  Mono.Tests       룸 상태머신·정책·클럭·아카이브 회귀 테스트
```

의존 방향: Control/Output/Core → Protocol, Shared. Control/Output은 Core 프로젝트를 참조하지 않는다.
